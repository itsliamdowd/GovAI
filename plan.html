Measured before (node script, cached data only)

  • rag.addDocs() rebuilt the whole BM25 from scratch on every call: 4.2 s each, called 4× at startup (council+transcripts, GIS, news, news-again) ≈ 17 s, and again on every daily/30-min refresh.

  • Council minutes/agendas were not indexed at all: loadCouncilCache() required data/council/meetings.json, which doesn't exist, so it returned 0 docs although 395 meeting files (11 MB) are cached. Council search was answering from transcripts only.

What changed

  • rag.js — BM25 is now an incremental inverted index: post: Map<term,{ids,tfs}> + len[]; add() appends postings, search() scores only docs in the query terms' postings, then applies the kind/date filter and sorts the candidates. addDocs() appends (dedupe set kept across calls, returns the number added) — no rebuilds. searchText is dropped after indexing. Result cache: 256-entry LRU keyed by (method, k, filters, query), cleared when docs are added. queryDataset row cache capped at 500 entries. Council chunks index unigrams only (bigram vocabulary of 30k transcript chunks was most of the heap). rag.docCount getter.
  • council.js — loadCouncilCache() falls back to scanning data/council/city_council_*.json when meetings.json is absent, deriving the ingested list from the files.
  • test.js — addDocs returns count / re-add is a no-op; identical queries hit the cache.
